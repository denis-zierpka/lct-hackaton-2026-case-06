# Контур: оркестратор → оракул → кодер → ревьювер

Процесс перенесён из проекта Vikings Reborn (TypeScript, 2026-08…09) и подведён под
Kotlin/Android. Механика контура и хуки стек-независимы и перенесены без изменений;
всё, что касается команд, переписано под Gradle.

## Состав ролей

| Роль | Где живёт | Модель | Почему так |
| --- | --- | --- | --- |
| Оркестратор | главная сессия | Opus 5 | пишет спеки и приёмку — самая дорогая ошибка тут |
| `test-author` | подагент | Opus 5 | слабый оракул обесценивает весь контур |
| `coder` | подагент | Sonnet 5 | работа по готовой спеке с машинной приёмкой |
| `reviewer` | подагент | Opus 5 | ловить халтуру дороже, чем её делать |

Кодер на Sonnet 5 — сознательная экономия. Она безопасна ровно потому, что кодер
работает против оракула, который написан не им, и в границах, которые он не может
изменить. Если убрать эти два свойства, экономия сразу перестанет быть безопасной.

## Почему защита не в выборе модели

Инструкция «не правь тесты» — это просьба. Конструкция даёт три уровня, где каждый
следующий не зависит от предыдущего:

1. **`tools` в описании агента** — ревьювер не имеет `Edit`/`Write`, физически не может
   починить то, что должен оценить.
2. **`PreToolUse`-хук `guard-paths.js`** — перехватывает каждую запись кодера и каждую
   shell-команду, сверяет с whitelist. Fail-closed: нет файла скоупа, битый JSON,
   непонятный ввод — блокировка, а не пропуск.
3. **`SubagentStop`-хук `assert-oracle-intact.js`** — после завершения кодера сверяет
   `git diff` защищённых путей от HEAD. Работает независимо от отчёта кодера.

Ревьювер поверх этого — четвёртый слой, и он единственный, кто оценивает смысл, а не
факт. Поэтому на нём экономить нельзя.

## Цикл одной задачи

```
1. Оркестратор: пишет спеку по docs/TASK_TEMPLATE.md в docs/tasks/<ID>.md, коммитит
2. Оркестратор: base = HEAD, allow = файл оракула; пишет .claude/task-scope.json
3. @test-author  -> тесты в finny-pet/app/src/test/, обязаны быть КРАСНЫМИ
4. Оркестратор: сам гоняет тесты и проверяет ПРИЧИНУ красноты
                (ассерт на поведении, а не Unresolved reference / опечатка в имени)
5. Оркестратор: коммитит оракул; base = sha этого коммита;
                allow = файлы реализации, оракул переезжает в protect
6. @coder        -> реализация в пределах allow
                    SubagentStop-хук проверяет неприкосновенность protect
7. Оркестратор: гоняет ACCEPTANCE целиком сам (docs/ACCEPTANCE_PRESETS.md)
8. @reviewer     -> PASS | FAIL + FINDINGS
9. FAIL -> по адресату: coder / test-author / переписать спеку
   PASS -> оркестратор коммитит, поднимает base в task-scope до HEAD
```

Шаг 4 пропускать нельзя. Зелёный тест до реализации означает, что тест ничего не
проверяет. Красный по `Unresolved reference` — самый слабый красный: опечатка в
импорте выглядит так же, как отсутствующая функция. Для важной логики оркестратор
собирает в одноразовой копии дерева «ленивую» реализацию и требует, чтобы оракул
её завалил.

**Kotlin-ловушка шага 4.** Имя теста в обратных кавычках с `:` `.` `;` `[` `]` `/`
`<` `>` роняет `compileTestKotlin` целиком — ни один тест файла не исполнился,
а exit всё равно ненулевой и выглядит как «красный оракул». Проверять по XML-отчёту,
что тесты реально исполнены и упали на ассертах.

Перед каждым спавном кодера — проверка, что `allow` и `protect` не пересекаются
(правило №23 ниже):

```bash
python3 -c "import json;d=json.load(open('.claude/task-scope.json'));print([a for a in d['allow'] for p in d.get('protect',[]) if a.startswith(p)])"
```

## Базовый protect для этого проекта

```json
"protect": [
  "finny-pet/app/src/test/",
  "finny-pet/app/build.gradle.kts",
  "finny-pet/build.gradle.kts",
  "finny-pet/settings.gradle.kts",
  "finny-pet/gradle/",
  "finny-pet/gradle.properties",
  "finny-pet/gradlew",
  "finny-pet/app/proguard-rules.pro",
  "finny-pet/app/src/main/AndroidManifest.xml",
  ".claude/",
  "CLAUDE.md",
  "docs/"
]
```

Манифест в protect намеренно: новое разрешение — решение оркестратора (ТЗ 3.4).
`finny-pet/docs/` в protect не входит по умолчанию — туда кодер вносит правки доков
по своей задаче, но только перечисленные в `allow`.

## Внешний контур: пак и гейт

1. **Старт.** Оркестратор пишет пак задач в `docs/tasks/`, указывает ветку
   (`feat/<имя>`). Промпты пишутся в момент старта — им нужны реальные пути и
   сигнатуры из кода.
2. **Исполнение.** Задачи пака идут по циклу выше, в порядке зависимостей.
   Каждая задача = пара коммитов: `test(<ID>): …` с оракулом и `<ID>: …` с
   реализацией, где в теле — фактические CHECKS, вердикт ревьювера, найденные дефекты.
3. **Гейт.** Сеньор смотрит дифф целиком и живое приложение по чек-листу,
   выносит вердикт. Замечания → правки в той же ветке.
4. **Мердж и пуш** — только сеньор.

## Проверка вживую

**Экран смотрит оркестратор на эмуляторе, плавность и телефон — человек.**
`tools/emu.sh start → install → launch → shot → stop`. Для UI-задачи оркестратор
прикладывает скриншоты «до» и «после» к приёмке. Чего эмулятор НЕ показывает:
плавность анимаций (нет видеокарты), поведение на слабом телефоне, звук.
Это остаётся в чек-листе для сеньора.

Замер холодного старта (`am start -W`, 2026-09-23, эмулятор): `classic` 1,7 с,
`game` 3,8 с — оба в нормативе ТЗ 3.4 (≤ 5 с), но `game` с запасом 1,2 с,
и на эмуляторе без видеокарты. Решающий замер — на телефоне.

ТЗ 3.1.3 требует проверку на физическом устройстве от 3 ГБ — это задача сеньора
перед сдачей, результат идёт в `finny-pet/docs/TEST_CASES.md`.

## Что не отдаётся кодеру

- Нарезка задач, архитектурные решения, выбор варианта сборки.
- Формулы экономики и числа в `content.json`/`rules` — решение оркестратора и сеньора.
- Тексты для ребёнка, объяснения последствий, формулировки заданий — ими проверяется
  соответствие ТЗ 3.5 и рамке; пишет оркестратор, кодер переносит.
- Подпись и релизная сборка, разрешения в манифесте.
- Правки спек, `CLAUDE.md`, этого документа и гейт-ревью.

## Принципы нарезки

- Одна задача = связный кусок, проверяемый тестом или чек-листом, в идеале ≤ день.
- XL дробим до старта. Зависимости — явные.
- Спорные числа не «выдумываем», а помечаем `[TBD]` и решаем отдельно.

## Правила, выведенные из практики

**Происхождение.** Правила 1–23 куплены ошибками в проекте Vikings Reborn
(TypeScript, Phaser, Fastify, Vitest, 2026-08-21…09-03) и перенесены ДОСЛОВНО.
Почти все описывают класс ошибки, а не инструмент. Читать с заменой:
`npm test`/`vitest` → `./gradlew test…UnitTest`, `*.test.ts` → `app/src/test/**/*.kt`,
`dist` → собранный APK, «голдены», «квесты», «энкаунтеры», `exclusiveGroup` —
понятия той игры; смысл правила — в описанном классе ошибки. Правило №22 — про
то, что развилку контента надо закрывать существующими примитивами, а не новой
механикой; здесь его аналог — «новое задание через `content.json`, а не код».

Новые правила этого проекта добавляются с №24 (дальше — №25), с датой и задачей, на которой куплены.

24. **Перенос guard в проект с подкаталогом требует живого зонда на НОВОЙ раскладке
    (2026-09-22, перенос контура).** Скопированный `guard-paths.js` прошёл все 34
    собственных кейса — и пропускал `cd finny-pet && sed -i … app/src/test/X.kt`.
    Фильтр искал в команде полный путь из `protect` (`finny-pet/app/src/test/`),
    а после `cd` в команде остаётся только хвост. Собственный набор кейсов этого
    не видел: он написан под раскладку, где проект лежит в корне. Лечение —
    сверять и хвосты пути от двух сегментов; три новых кейса проверены на старом
    хуке и там КРАСНЕЮТ (контроль, что кейс вообще что-то ловит).
    Правило: после переноса контура гнать не только его тесты, но и зонд с
    командами в том виде, в каком их напишет кодер именно в этом репозитории.

Двадцать три правила, каждое куплено ошибкой в реальной задаче. Они дополняют инварианты из
CLAUDE.md, а не заменяют их. (Правила 6–9 добавлены 2026-08-22, 10–12 — 2026-08-23,
13–16 — 2026-08-24, 17–19 — 2026-08-25, 20–21 — 2026-08-29/30, 22 — 2026-09-02, 23 — 2026-09-03.)

1. **Оракул проверяет ПОСЫЛКУ спеки, а не только реализацию.** Спека — такой же артефакт с
   ошибками, как код. В BPR-T01 оракул прогнал обучающую цепочку и показал, что таблица цен из
   спеки её не проходит: спека насчитала два здания вместо трёх и забыла про наймы. Если
   спека утверждает что-то проверяемое («последовательность проходится», «голдены не
   сдвинутся»), это утверждение обязано стать тестом.
2. **Тесты не ловят устаревшую прозу.** Комментарий или дока, противоречащие изменённому коду
   рядом, проходят любую зелёную приёмку. Меняешь правило — прогоняй сквозной grep по
   ФОРМУЛИРОВКЕ правила по всему репозиторию, а не только по коду, который правишь.
3. **Зависимость ставит оркестратор и проверяет живым смоуком.** `npm install <plugin>` без
   версии тянет мажор под свежий фреймворк: дважды за сессию прилетал пакет под Fastify 5 при
   нашем Fastify 4, и плагин упал бы при регистрации. Проверять надо запуском, а не сверкой
   номеров, и до спавна кодера — иначе цикл кодера уходит в пустоту.
4. **Рискованную проверку оркестратор оставляет себе.** Перегенерация голденов, прогон
   docker-стека, восстановление из бэкапа, живая сверка через прокси — места, где самоотчёт
   агента ничего не стоит. Кодеру такие шаги прямо запрещаются в спеке, а в приёмке пишется,
   что их выполняет оркестратор.
5. **Не запускай приёмку параллельно с фоновым агентом, которому разрешено менять рабочее
   дерево.** Два одновременных `npm test` роняют тесты, чувствительные к таймингу (rate-limit,
   pglite-роуты), и выглядит это как настоящая регрессия. Ревьювер, проверяющий мутацией,
   владеет деревом единолично до конца проверки.
6. **Гигиена task-scope и protect-путей (2026-08-22).** Правки protect-путей (хуки, конфиги,
   launch.json) коммить ДО спавна кодера — незакоммиченные, они выглядят для стоп-хука
   правками кодера. После приёмки задачи поднимай `base` в `.claude/task-scope.json` до
   HEAD — иначе осиротевшая resumable-сессия кодера при следующем пробуждении увидит
   устаревший скоуп. Файл gitignored: на свежем клоне его нет, и fail-closed guard не даст
   спавнить кодера, пока оркестратор не запишет скоуп новой задачи — это ожидаемо.
7. **Оракул ловит дыры в спеке — читай его отчёт, а не только exit code (2026-08-22).**
   В TCK-T01 `test-author` сообщил, что `encounterDefToTs` собирает TS-литерал вручную и
   новое поле там не появится: автор задал бы лимит в редакторе, скопировал код — и лимит
   молча потерялся бы. Тесты этого не показали бы никогда, потому что оба конца были бы
   согласованы. Спека дополнена разделом до спавна кодера. Если агент пишет «пробел
   контракта» — это находка, а не шум.
8. **Красный тест бывает сторожем, а не поломкой (2026-08-22).** Добавление квеста с
   самоцветами уронило пин `GEM-T01`, который держит закрытый список заданий с гем-полями.
   Тест сработал ровно как задуман: потребовал подтвердить, что новое задание — осознанное
   решение, а не протечка. Такой пин обновляет `test-author`, НЕ оркестратор (инвариант
   контура №1 действует и на оркестратора), и после правки сторож проверяется живьём:
   подсунь лишний элемент — тест обязан упасть, убери — позеленеть.
9. **Правка ассетов пользователя — тоже изменение, требующее проверки (2026-08-22).**
   Фейд 12 мс, поставленный «чтобы убрать щелчок» на музыкальных петлях, дал провал
   громкости на стыке (−8.4 dB у боевого трека) и слышимую микропаузу — дефект нашёл
   пользователь на слух. Правильный приём для петли — равномощный кроссфейд хвоста в
   собственное начало (cos/sin), а проверять надо не только разрыв волны, но и уровень
   громкости на стыке против середины трека. Пересобирать всегда из ОРИГИНАЛОВ.


10. **Проза в ДОКАХ ломается так же, как в коде, и тестами не ловится (2026-08-23).**
    За сессию ревью дало FAIL четыре раза, и КАЖДЫЙ раз — за устаревшую документацию, ни
    разу за код. Дважды это была операционная инструкция, которая отправляла сеньора
    проверять несуществующее поведение (петля длиннее окна звучания; «Точно? Да» после
    замены на модалку). Вывод: греп по формулировке гнать по ВСЕМУ репозиторию сразу, а
    не по файлу, на который указал ревьювер — трижды подряд ложь находилась ещё в двух
    местах. Автоматизировано: `scripts/docs-audit.py` сверяет доки с кодом по фактам
    (константы, длительности аудио, размеры ассетов, наличие файлов) — гонять перед
    релизом и после смены любой константы.
11. **Sha-пин в живом документе врёт по построению (2026-08-23).** `PLAYTEST_CHECKLIST.md`
    дважды содержал коммит, на котором приёмка была КРАСНОЙ: документ правится в тех же
    сессиях, что и код, поэтому записанный sha устаревает раньше, чем до плейтеста дойдут
    руки. Пин убран совсем, вместо него — команда прогона на своём HEAD.
12. **Смена собственного правила требует явного снятия пина (2026-08-23).** MUS-T04
    запретил вторую константу длительности, `test-author` закрепил запрет тестом. Когда
    сеньор попросил длинный переход, этот тест встал стеной — и правильно. Оракул вернул
    BLOCKED с вопросом на 22 сломанных пина; разрешение далось явно, с рамками (править
    только ставшее ложным, покрытие не ослаблять, тесты не удалять). Пины обновляет
    `test-author`, инвариант контура №1 действует и на оркестратора.
13. **Прототип обязан воспроизводить КОНТЕЙНЕР, а не только элемент (2026-08-24).**
    Согласовали ширину ячеек зданий на прототипе, приёмка дала «11 из 11 пройдено» —
    вердикт был ЛОЖНЫЙ. Я мерил во всю ширину окна, а панель зданий открывается на
    `min(980px,94%)` (`villageHud.ts`, `overlayPanel`). В настоящей ширине ценник
    разваливался надвое у трёх зданий из семнадцати. То же повторилось с карточкой
    воина: страница показывала пустую вкладку «Руны» («Постройте Алтарь»), то есть
    проверялся самый лёгкий случай вместо тяжёлого. Вывод: приёмочная страница
    воссоздаёт реальные размеры и реальное наполнение, иначе проверяет саму себя.
14. **Зонд начинается с самопроверки — иначе он врёт молча (2026-08-24).** За сессию
    измерители соврали пять раз, каждый по-своему: мерили не тот уровень DOM (части
    ценника лежат на два уровня глубже) и печатали «переносов нет» при видимых на
    скриншоте переносах; считали нулевые размеры схлопнутой модалки за успех и выдали
    «5/5 пройдена»; хватали первый элемент с `top:46px` — а это была карта мира, не поле
    деревни; искали блок по строке `77vh`, которой уже не было, и молча переставали
    проверять главное. Правило: зонд сначала ЛОМАЕТ проверяемое (сжимает кнопку,
    подставляет заведомо плохое значение) и обязан это заметить; не заметил — отказывается
    печатать вердикт. Плюс санити на нули: `0` — это «не вижу», а не «всё хорошо».
15. **Связанные числа выражать одно через другое, а не дублировать (2026-08-24).**
    Верхний блок деревни был зашит как `calc(77vh - 46px)`, и рядом стоял комментарий
    «77vh = 100 − 23». Число было связано с высотой нижней панели ПО СМЫСЛУ, но не в
    коде. Смена панели на `max(20vh,162px)` их развела: между полем и панелью появилась
    полоса пустоты 4–43px в зависимости от экрана, видимая глазом. Лечение — выразить
    верх через ту же величину (`calc(100vh - 46px - max(20vh,162px))`) и поставить пин
    именно на это выражение, а не на «какое-нибудь calc».
16. **FAIL ревью бывает адресован не тому — проверяй, был ли у исполнителя путь
    (2026-08-24).** Ревьювер справедливо забраковал хак (`title` протащили через параметр
    `style`, досрочно закрыв атрибут) и назначил виновным кодера. Но пин оракула требовал
    `title` ВНУТРИ тега `<img>`, а `iconImg()` такого параметра не имеет и `icons.ts` был
    вне allow: повесь кодер `title` на обёртку — тест бы упал. Правильного решения у него
    не существовало, корень был в формулировке спеки («title на иконке»). Порядок
    исправления: сначала `test-author` правит пин, потом кодер — реализацию. Обратный
    порядок заставляет кодера подгоняться под неверный тест.

17. **Пин, проверяющий НАЛИЧИЕ строки в коде, не проверяет ЭФФЕКТ (2026-08-25).**
    В RES-T02 пин требовал `max-width:728px` в разметке и был бы зелёным на правке,
    которая визуально не меняет НИЧЕГО: панель `position:fixed` без явной `width` —
    shrink-to-fit, и замер на собранном `dist` дал 322px и при 560px, и при 728px.
    Ложноположительный пин хуже отсутствующего: он выдаёт мандат на «сделано».
    Правило: если пин про геометрию/визуал, он обязан либо сверяться с фактическим
    замером, либо требовать конструкцию, БЕЗ которой эффект физически недостижим
    (здесь — явную `width`). Проверять пин подстановкой ОБЕИХ сторон: он должен
    краснеть на «косметической» правке и зеленеть только на настоящей.
18. **Прототип врёт в числах, приёмочные утверждения делать по замеру на `dist`
    (2026-08-25).** Продолжение правила №13, но про другое: прототип может
    воспроизводить контейнер верно и всё равно ошибаться, потому что не содержит
    полного контента (иконки, шрифты, реальные отступы). В RES-T02 прототип обещал
    «на 1280×720 прокрутки нет» — на реальной сборке она была, и это ложное
    утверждение успело попасть в спеку, в ACCEPTANCE и в две доки, откуда его вынул
    ревьювер. Числа прототипа — ориентир для ПОДБОРА; всё, что уходит в критерий
    приёмки и в доки, меряется на собранном `dist`.
19. **Правку доки делать в САМОМ утверждении, а не примечанием рядом (2026-08-25).**
    Найдя ложный критерий в ACCEPTANCE, я дописал абзацем выше «формулировка неточна,
    читать по таблице» — и оставил ложь на месте. Ревьювер справедливо вернул FAIL:
    канонический критерий читают отдельно от пояснений, и следующая сессия поверит
    именно ему. Чинится источник, а не приписка к нему; после исправления примечание
    само становится ложью и удаляется.
20. **Оракул коммитить ДО спавна кодера — иначе проверка его целостности слепа
    (2026-08-29, находка ревьювера на PSC-T01).** Команда приёмки
    `git diff --name-only $BASE -- "*.test.ts"` не видит **untracked** файлы в
    принципе. Когда оракул — новый файл и он ещё не закоммичен, эта проверка
    возвращает «пусто» независимо от того, что кодер с ним сделал: она даёт
    ложноположительный мандат «оракул не тронут». Проверено фактом: оба тестовых
    файла лежали в дереве, `git diff` показывал пусто.
    Правильный порядок (он же в скилле `agent-contour-orchestration`):
    оракул → проверка красноты → **коммит оракула** → `base` = sha этого коммита →
    только потом спавн кодера. Тогда `git diff --name-only $BASE -- "*.test.ts"`
    сравнивает с ЗАКОММИЧЕННЫМ оракулом и ловит подмену.
    До этого целостность держалась только на `guard-paths.js` — одном слое вместо двух.
21. **Стенд оракула, готовящий состояние заранее, скрывает ветку «первого раза»
    (2026-08-30, PSC-T06, дефект дожил до прода).** Оракул PSC-T02 проверял выдачу
    обучающего заклинания на `GET /village` — 31 тест, все зелёные. Но каждый его
    стенд (`standWith`/`freshApp`) СНАЧАЛА писал деревню в БД, поэтому ветка
    `if (!rec)` (создание деревни при первом входе) не исполнялась НИ РАЗУ.
    В ней грант стоял ПОСЛЕ возврата ответа — новый игрок не получал заклинание,
    оно приходило только со второго запроса. Нашла живая проверка на проде,
    не тесты.
    Правило: если у кода есть ветка «сущности ещё нет / первый запуск / пустое
    состояние», оракул обязан иметь стенд, который её РЕАЛЬНО исполняет, и
    утверждать это явно (`expect(await getVillage(db, id)).toBeNull()` перед
    действием). Удобный стенд, который «подготовил всё как надо», проверяет
    только тёплый путь.
    Сопутствующее: пин на такую ветку сверять не только по телу ответа, но и по
    ПЕРСИСТЕНТНОМУ состоянию (снапшот в БД) и по последствию (в PSC-T06 — что
    выданный каст реально применим в бою). Иначе «дорисовка в ответе» проходит
    зелёной.
22. **Развилку в контенте закрывать `exclusiveGroup`, а не новой механикой
    (2026-09-02, поправка сеньора на спеке SQ34-T05).** Оркестратор увидел в спеке
    арки поле `nextQuestModifier` («эффект на следующий бой») и собрался заводить
    подмену энкаунтера по метке — как `stoneFordEncounter` в T04. Сеньор напомнил:
    механику взаимоисключающих квестов завели в T04 ровно для таких случаев.
    **Почему подмена хуже, в терминах сторожей:** энкаунтер, подменённый по метке,
    для реестра остаётся ОДНИМ квестом. Сторож достижимости прогонит одну ветку из
    трёх (`routePlans` о них не знает), сторож бюджета посчитает развилку как один
    вклад. Две ветки останутся непроверенными навсегда — тот же класс слепоты, что
    «сумма XP вместо пути» (правило №7). Три квеста в `exclusiveGroup` оба сторожа
    видят: бюджет считается по минимуму группы, достижимость гоняется по каждой ветке.
    Порядок выбора средства при любой развилке:
    `QuestChoice.storyFlag` → `requiresStoryFlag` → `exclusiveGroup` →
    `requiresQuestFromGroup`. Новое поле/вид/модификатор — только после того, как в
    спеке показано, чего именно из этого списка не хватает.
    Исключение, где подмена уместна: метка НЕ создаёт развилку, а смягчает один и тот
    же бой (T04, `stone_ford_hint_received` → вторая волна на 5 с позже). Признак:
    состав врагов и награда те же, ветвления контента нет.
23. **`allow` и `protect` в `task-scope.json` не должны пересекаться (2026-09-03, две
    задачи подряд).** Обновляя скоуп с шага «оракул» на шаг «кодер», оркестратор менял
    `allow` на файлы реализации, но `protect` оставлял прежним — а там те же файлы
    (или их каталог, например `docs/`). Стоп-хук `assert-oracle-intact.js` сверяет
    protect-пути с HEAD и, увидев правки кодера в них, велит вернуть `STATUS: BLOCKED`.
    Кодер оба раза отработал ПРАВИЛЬНО: не откатывал чужое, а остановился — но круг был
    потрачен, а отчёт пришёл без содержания («ничего не меняю, останавливаюсь»).
    **Симптом:** `STATUS: BLOCKED` с пустым QUESTION при том, что файлы в дереве изменены
    и тесты по ним зелёные. Не читай это как отказ работать — проверь пересечение.
    **Проверка перед каждым спавном** (одна строка, дешевле круга):
    ```
    python3 -c "import json;d=json.load(open('.claude/task-scope.json'));
    print([a for a in d['allow'] for p in d.get('protect',[]) if a.startswith(p)])"
    ```
    Пусто — можно спавнить. Непусто — убрать эти пути из `protect`.
    Частный случай: `docs/` в protect и `docs/GDD.md` в allow — тоже пересечение,
    хук сравнивает по префиксу.


## Известные ограничения

Перенесены из Vikings Reborn с той же оговоркой о происхождении. Пункты про pglite,
Chrome/CDP-зонды и Docker относятся к той игре и здесь не применимы, оставлены ради
класса ошибки («приёмка рядом со вторым прогоном недостоверна», «зонд говорит со
старым процессом»). Для Gradle аналог первого пункта: не запускать приёмку, пока в
фоне работает агент, которому разрешено трогать дерево, или второй `./gradlew`.

- **Приёмка НЕДОСТОВЕРНА, если рядом крутится второй прогон (2026-08-25, замер).**
  Правило №5 говорило об этом словами; вот числа. Машина: 3 ядра, 5 ГБ. Vitest по
  умолчанию занимает все ядра, а серверные тесты на pglite (`app.test.ts`,
  `pvp.test.ts`, `village.test.ts`) поднимают БД в памяти и живут при дефолтном
  таймауте 5000 мс. Когда прогонов два, им не хватает CPU:

  | как гоняли | результат |
  | --- | --- |
  | `npx vitest run packages/server` изолированно | 100 passed, exit 0 |
  | весь `npm test` последовательно (6 раз подряд) | 1895 passed, exit 0 |
  | два `npm test` одновременно | 3–4 падения, **все** `Test timed out in 5000ms` |

  Падают ВСЕГДА только серверные pglite-тесты и всегда по таймауту, не по ассерту.
  Как отличить от настоящей регрессии за одну команду: посмотреть причину. Строка
  `Test timed out in 5000ms` у серверного теста при зелёном изолированном прогоне
  `npx vitest run packages/server` = помеха, а не поломка. `AssertionError` = поломка.

  Практика для оркестратора: перед приёмкой убедиться, что фоновых прогонов нет
  (`process(action='list')` и `pgrep -f vitest`), и не запускать `npm test` рядом с
  фоновым агентом, которому разрешено трогать рабочее дерево. Наступил на это в
  RES-T03: первый прогон дал 6 падений при живом фоновом прогоне, следующие шесть —
  чистые 1895.
- **Подагенты не могут запускать `npm`/`npx`/`node` (2026-08-25).** В сессиях
  `test-author`, `coder` и `reviewer` любая исполняющая команда возвращает
  «This command requires approval» без интерактивного канала подтверждения; при этом
  `git`, `cat`, `grep`, `ls`, `find` работают. Это ограничение песочницы, а НЕ
  `guard-paths.js` (он вообще применяет правила только к `agent_type === "coder"`).

  **Уточнение 2026-09-02: ограничение НЕПОСТОЯННО.** В этой сессии `test-author` дважды
  сумел прогнать `npx vitest` и `npx tsc` и привёл числа, которые СОВПАЛИ с прогоном
  оркестратора до штуки (60 failed | 205 passed; затем 10 failed | 78 passed). То есть
  запрет то действует, то нет — в том же репозитории, в тот же день, у той же роли.
  Следствия для оркестратора:
  1. Разрешение запускать команды агенту НЕ выдаётся автоматически — в промпте
     по-прежнему пишем «прогонов у тебя нет» и требуем честного признания в CHECKS.
     Кодер того же дня честно ответил «не запускал, это задача оркестратора» — значит
     формулировка работает.
  2. **Числа агента остаются непроверенными до прогона оркестратора**, даже когда они
     правдоподобны и даже когда агент их действительно получил. Совпадение чисел —
     не доказательство: в прошлую сессию кодер выдумал числа, случайно совпавшие с
     реальными (урок №5 пака SQ34).
  3. Приёмка инварианта контура №2 гоняется оркестратором ЦЕЛИКОМ и всегда — вне
     зависимости от того, что агент приложил к отчёту.

  Практические следствия, проверенные на UNW-T01 и RES-T01:
  - **Оракул физически не может показать, что тесты красные.** Шаг 4 цикла
    (прогнать и убедиться, что падают по правильной причине) целиком переходит к
    оркестратору. Пропускать его нельзя — именно он ловит тест, который падает на
    синтаксисе вместо отсутствия реализации.
  - **Инвариант контура №3 («ревьювер запускает приёмку сам») сейчас неисполним.**
    Ревьювер честно отказался давать PASS без прогона и вынес FAIL — формально
    правильно, но круг был потрачен. Рабочий приём: в промпте ревьюверу сразу
    сказать, что приёмку запускать не нужно, и дать ФАКТИЧЕСКИЙ вывод команд
    оркестратора, оставив ревьюверу статическую проверку (диф, границы, доки).
    Это ослабляет контур — ревьювер верит чужим числам, — поэтому оркестратор
    обязан гонять приёмку честно и полностью, а не выборочно.
  - Не тратьте ходы агента на попытки обойти: перебор `npx vitest`,
    `node node_modules/.bin/vitest`, `env` даёт тот же отказ.
- **Зонд обязан проверять, что порт отладки свободен (2026-08-25).** Chrome с
  прошлого прогона остаётся жив на том же `--remote-debugging-port`, и новый зонд
  через `/json/list` подключается к СТАРОЙ вкладке с чужой страницей и её кешем.
  Симптом обманчив: замеры приходят «валидные», но относятся к прошлому состоянию.
  На RES-T01 это стоило круга — сначала все картины были нулевого размера
  (`onerror` скрыл их из-за 404 под `file://`), а после перехода на http зонд
  продолжал видеть нули, потому что говорил со старым браузером.
  Лечение в самом зонде: перед стартом дёрнуть `/json/version`, и если порт занят —
  отказаться работать с явным сообщением, а не подключаться.
  Второе следствие: страницы с абсолютными путями (`/assets/...`) обязаны
  открываться по http, под `file://` они молча деградируют через `onerror`.


- **Bash-фильтр в `guard-paths.js` эвристический.** Полный разбор shell-команды
  невозможен; экзотические конструкции пройдут. Именно поэтому существует слой 3 —
  он проверяет результат, а не намерение, и обойти его нельзя.
- **`git checkout <sha> -- <protected>` проходит оба слоя** (найдено на GEM-T01,
  2026-08-21): фильтр слоя 2 не распознал команду как запись, а слой 3 сверяет диff
  от BASE — откат защищённого пути К BASE даёт пустой диff и не детектится. Кодер
  так снёс незакоммиченную правку оркестратора в `.claude/launch.json` (по
  добросовестной причине — чистил «грязь» из диффа). Ущерб ограничен: уничтожение
  незакоммиченного состояния, подменить оракул этим нельзя. Вывод: незакоммиченные
  правки protect-путей до спавна кодера либо коммить, либо считать расходником.
- **PreToolUse из frontmatter агента в CC 2.1.235 молча не вызывается** (диагноз
  2026-08-21, негативный зонд; схема frontmatter сверена с докой дословно — не наша
  ошибка). Зонд-кодер тогда беспрепятственно выполнил `git checkout`, создал файл
  вне allow и дописал в защищённый оракул. **ПОЧИНЕНО в тот же день (решение
  сеньора):** `guard-paths.js` объявлен PreToolUse-хуком в `.claude/settings.json`
  (там хуки работают и в подагентах, хот-релоад подтверждён) и дёргается на каждом
  вызове сессии; ограничения применяет только к `agent_type === "coder"` из stdin
  (поле проверено дампером; у main-сессии его нет). Контрольный зонд: все три
  запрещённые операции блокируются. Остаточный риск — fail-open при переименовании
  поля в будущих версиях CC; поэтому ПРАВИЛО: после каждого обновления Claude Code
  гонять не только `node .claude/hooks/guard-paths.test.js` (логика), но и живой
  негативный зонд — кодера с заданием выполнить запрещённую операцию (подключение).
  `hooks:` в frontmatter `coder.md` оставлен: вреда нет, а на версиях, где он
  работает, даст дублирующий слой.

  **Уточнение 2026-08-24 (ONB-T02, круг 2).** Область защиты уже проверена зондом и
  оказалась УЖЕ, чем звучит выше: `guard-paths.js` ограничивает ТОЛЬКО `agent_type ===
  "coder"`. Проверено дампером на живом хуке:

  | вход | результат |
  | --- | --- |
  | `{"agent_type":"coder","tool_name":"Write","file_path":"docs/BACKLOG.md"}` | exit 2 — блок |
  | `{"agent_type":"test-author", …}` | exit 0 — пропуск |
  | без `agent_type` (обёртка `claude -p`, главная сессия) | exit 0 — пропуск |

  Практическое следствие, стоившее круга: правки в `docs/` и коммиты, которые в отчётах
  выглядели как «кодер вышел за whitelist», делал НЕ подагент-кодер, а обёртка-оркестратор
  (`claude -p …`), на которую хук не распространяется вовсе. Она же игнорирует запрет
  «НЕ КОММИТЬ» — блокировка git-мутаций тоже висит только на кодере.

  Вывод для оркестратора: **whitelist защищает от кодера, но НЕ от обёртки.** Всё, что
  обёртка делает вне скоупа, ловится только приёмкой (`git status` + `git diff --name-only`
  после каждого захода) — гонять её обязательно, а не по настроению.
- **Слой 3 сверял protect с base и велел «откатить»** — оба свойства укусили
  2026-08-21: после коммита оркестратора в protect-пути base устаревал, стоп-хук
  вечно краснел у осиротевших сессий кодера, а текст «откатите эти файлы» дважды
  заставил кодера снести незакоммиченный файл оркестратора. **ПОЧИНЕНО (решение
  сеньора):** сверка идёт с HEAD (кодер не коммитит — его правки всегда
  незакоммичены), текст — «ничего не откатывай, верни STATUS: BLOCKED».
  Закоммиченную подмену оракула этот хук больше не ловит — её ловит ACCEPTANCE
  (`git diff --name-only $BASE -- "*.test.ts"` → пусто) у ревьювера и оркестратора.
- **Docker расширяет поверхность обхода.** Контейнер с bind-mount репозитория пишет
  в хостовую ФС мимо `Edit`/`Write`. Guard ловит связку «docker + `-v`/`--mount` +
  защищённый путь», но контейнер, смонтировавший каталог под другим именем, пройдёт.
  Держите `Dockerfile`, `docker-compose*.yml` и файлы зависимостей в `protect`:
  изменение образа переопределяет условия прогона оракула, то есть саму приёмку.
- **Ревьювер обязан использовать `docker compose run --rm`, а не `exec`.** `exec`
  заходит в контейнер, который кодер мог наполнить чем угодно, и проверяет следы
  его работы вместо репозитория.
- **`isolation: worktree` намеренно не включён** у кодера. Worktree ветвится от
  default branch и не увидит незакоммиченный `.claude/task-scope.json`, из-за чего
  fail-closed хук заблокирует кодера полностью. Если нужна изоляция —
  коммитьте `task-scope.json` в ветку задачи перед спавном.
- **Контур не спасает от плохой спеки.** Он превращает «модель схитрила» в
  «мы плохо описали задачу», что диагностируется и чинится. Это и есть цель.
- **Стоимость.** Три подагента на задачу вместо одной сессии. Оправдано там, где
  цена незамеченной халтуры выше цены токенов.
